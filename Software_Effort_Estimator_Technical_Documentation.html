Software Effort Estimator

FAHP-Weighted Kernel SVR with SHAP Explainability
Based on: Sehra et al. (2018), "Software Effort Estimation using FAHP and LSSVM"
Dataset: COCOMO-81  ·  n = 63 projects  ·  17 cost drivers
LOO-MMRE: 0.3132  ·  80% PI: [−40%, +64%]
Abstract
This document describes the full technical implementation of a software effort estimation system based on Sehra et al. (2018). The system combines Fuzzy Analytic Hierarchy Process (FAHP) feature weighting — derived from Chang's (1996) extent analysis — with a weighted-kernel Support Vector Regression (SVR) model trained on the COCOMO-81 benchmark (63 projects, 17 cost drivers). SHAP KernelExplainer is applied post-hoc to provide instance-level explanations in person-months. Leave-One-Out cross-validation yields LOO-MMRE = 0.3132, improving on the paper's reported MMRE = 0.57.

1. Introduction & Motivation

Software project cost overruns are a persistent industry problem. Studies consistently report that 50–80% of software projects exceed their initial estimates (Standish Group CHAOS Report). Accurate effort estimation at the planning stage is critical for budgeting, staffing, and delivery scheduling.

Classical estimation models such as COCOMO-81 (Boehm 1981) provide deterministic formulas based on Lines of Code and a set of cost driver multipliers. While transparent, these models treat all features as equally weighted and cannot learn non-linear interactions from historical project data.

This system addresses both limitations by:

  • Using FAHP to assign data-driven importance weights to each of the 17 COCOMO-81 cost drivers before training.
  • Using a weighted-kernel SVR that embeds those weights directly into the RBF kernel, so the model learns in a feature-importance-aware space.
  • Using SHAP to explain each individual prediction in human-readable person-month contributions per feature.
Mitacs research angle: The COCOMO-81 dataset is 40+ years old. Modern software teams generate richer signals daily — Jira sprint velocity, GitHub PR metrics, Copilot adoption rates. The Mitacs proposal is to apply this validated methodology to a company's own historical project data, producing a company-specific estimator with significantly lower MMRE.

3. Fuzzy AHP Feature Weighting (Chang 1996)

Analytic Hierarchy Process (AHP) is a structured technique for deriving relative importance weights from pairwise comparisons. The Fuzzy extension (FAHP) uses Triangular Fuzzy Numbers (TFNs) instead of crisp values to handle the inherent uncertainty in expert judgments.

3.1 Triangular Fuzzy Numbers

A TFN is written as M = (l, m, u) where l is the lower bound, m is the modal (most likely) value, and u is the upper bound. The standard FAHP scale maps importance levels 1–9 to TFNs:

LevelTFN (l, m, u)Interpretation
1(1, 1, 1)Equal importance
3(1, 3, 5)Moderate importance
5(3, 5, 7)Strong importance
7(5, 7, 9)Very strong importance
9(7, 9, 9)Extreme importance

Reciprocals use the inverse TFN: (l, m, u)⁻¹ = (1/u, 1/m, 1/l).

3.2 Pairwise Matrix Construction

In the original Sehra et al. (2018) paper, pairwise matrices are constructed manually by domain experts. In this implementation, they are derived automatically from the COCOMO-81 data using the following steps:

  1. Compute FAHP project-level weights from the effort and LOC distributions of all 63 training projects.
  2. Compute the Spearman correlation between each feature column and the project weights.
  3. Use the correlation ratios to build the pairwise TFN comparison matrix via continuous interpolation of the TFN scale.

3.3 Synthetic Extent Values (Chang 1996)

For each row i of the pairwise matrix, the fuzzy synthetic extent value Si is:

S_i = (Σ_j l_ij / Σ_i Σ_j u_ij , Σ_j m_ij / Σ_i Σ_j m_ij , Σ_j u_ij / Σ_i Σ_j l_ij)
(Chang 1996, Eq. 4)

3.4 Degree of Possibility

The degree of possibility that fuzzy number M₁ ≥ M₂ is defined as:

V(M₁ ≥ M₂) = 1, if m₁ ≥ m₂ 0, if l₂ ≥ u₁ (u₁ − l₂) / ((m₂ − l₂) − (m₁ − u₁)), otherwise
(Chang 1996, correct formula)
Note on Sehra et al. (2018) Equation 5: The paper's denominator shows (m₂ − l₂) − (m₁ − l₁), which contains a typographic error. The correct denominator uses u₁ (upper bound of M₁), not l₁ (lower bound). This implementation uses the correct Chang (1996) formula as shown above.

3.5 Weight Derivation

For each feature i, the minimum degree of possibility against all other features gives the unnormalised priority weight:

W'_i = min_{j ≠ i} V(S_i ≥ S_j)
(Chang 1996, Eq. 7)

Normalising so the weights sum to 1 gives the final FAHP weight vector θ = (θ₁, θ₂, …, θ₁₇).

4. Weighted-Kernel SVR (Sehra et al. 2018)

Standard SVR uses an RBF kernel that treats all features as equally important. The key contribution of Sehra et al. (2018) is embedding the FAHP weights directly into the kernel, so feature similarity is measured in a weighted feature space.

4.1 Standard RBF Kernel

K(x_k, x_l) = exp(−γ ‖x_k − x_l‖²)

4.2 FAHP-Weighted Kernel (Sehra et al. 2018, Eq. 17)

Each feature dimension is scaled by the square root of its FAHP weight, so higher-importance features contribute more to the distance calculation:

K_θ(x_k, x_l) = exp(−γ ‖√θ ⊙ (x_k − x_l)‖²)
where ⊙ is element-wise multiplication

In practice this is implemented by pre-multiplying the feature matrix:

X_w = X_scaled × √θ

and then training a standard RBF SVR on X_w. This is mathematically equivalent to the weighted kernel.

4.3 SVR Objective

SVR minimises:

(1/2) ‖w‖² + C Σ_i (ξ_i + ξ_i*) subject to: y_i − ⟨w, φ(x_i)⟩ − b ≤ ε + ξ_i ⟨w, φ(x_i)⟩ + b − y_i ≤ ε + ξ_i* ξ_i, ξ_i* ≥ 0

The ε-tube defines an insensitive zone; points within ε of the prediction incur no penalty. C controls the trade-off between flatness and tolerance of deviations beyond ε.

5. Training Pipeline

All preprocessing steps applied at training time are re-applied identically at inference time (including inside the SHAP pipeline) to prevent train-serve skew.

Step-by-step

  1. Log transform: X_log = log(clip(X_raw, 1e-3))
    Compresses the 3-order-of-magnitude range of LOC values and linearises the power-law relationships in COCOMO. Also separates Dev Mode ordinal values (log(1)=0, log(2)=0.69, log(3)=1.10).
  2. MinMaxScaler: Scales all features to [0, 1] so the RBF kernel distance is not dominated by features with large raw values.
  3. FAHP weighting: X_w = X_scaled × √θ
    Embeds FAHP priorities into the feature space.
  4. Target transform: y_log = log1p(y_raw), then MinMaxScale to [0, 1]. Prediction is inverted with expm1(inverse_scale(SVR output)).

6. Hyperparameter Tuning

Three hyperparameters are tuned: regularisation C, kernel width γ, and the ε-insensitive tube width ε. All tuning uses Leave-One-Out cross-validation (LOO-CV) with MMRE as the objective — the same validation metric used in the paper.

6.1 Mean Magnitude of Relative Error (MMRE)

MMRE = (1/n) Σ_i |actual_i − predicted_i| / actual_i

MMRE = 0 is perfect; values above ~0.5 indicate the average prediction is off by more than 50% of the actual effort.

6.4 Why ε matters

ε controls the width of the insensitive tube around the regression function. Smaller ε forces the model to fit more training points exactly (more support vectors, tighter fit). The original paper's LSSVM has no ε parameter — our grid over ε = {0.05, 0.1, 0.2} and the resulting fine search contributed to lowering LOO-MMRE from 0.4778 (after FAHP fix, without ε tuning) to 0.3132.

7. SHAP Explainability

FAHP gives a single global weight per feature — the same for every project. SHAP (Lundberg & Lee 2017) provides local explanations: for each individual prediction, it decomposes the result into per-feature contributions.

7.1 What SHAP computes

For a prediction f(x), SHAP finds values φ₁, φ₂, …, φₙ such that:

f(x) = E[f(X)] + φ₁ + φ₂ + … + φₙ
Additive feature attribution — each φᵢ is in person-months

where E[f(X)] is the baseline (average prediction over the training set).

7.2 KernelSHAP on original features

The SHAP values are computed in the original feature space — not the internal weighted/scaled space. This is achieved by wrapping the entire pipeline into a single function:

def full_pipeline(X_raw):
    X_log = log(clip(X_raw, 1e-3))
    X_sc  = scaler_X.transform(X_log)
    X_w   = X_sc × kernel_w          # kernel_w = √θ
    p_sc  = SVR.predict(X_w)
    p_log = scaler_y.inverse_transform(p_sc)
    return expm1(p_log)               # → person-months

explainer = shap.KernelExplainer(full_pipeline, X_raw_background)
shap_values = explainer.shap_values(x_raw, nsamples=150)

Background dataset: 30 randomly sampled training projects (raw feature values). Result: each SHAP value φᵢ is directly interpretable as the number of person-months that feature i adds to (or subtracts from) the baseline prediction.

8.2 Ablation Study — Does FAHP Actually Help?

To isolate the contribution of FAHP, the same SVR model was trained with identical hyperparameters (C=5, γ=1.5, ε=0.025) but with uniform feature weights (no FAHP). The same LOO-CV protocol was used.

ModelLOO-MMREImprovement
SVR, uniform weights (no FAHP) 1.0866 —
SVR + FAHP weighted kernel 0.3132 71.2% reduction in MMRE
Key finding: FAHP feature weighting is not cosmetic — it reduces prediction error by 71.2%. Without FAHP, the SVR model with the same hyperparameters produces LOO-MMRE > 1.0 (predictions off by more than 100% on average). This empirically validates the core contribution of Sehra et al. (2018).

8.3 Cross-Dataset Generalization (NASA-93)

The NASA-93 dataset (93 NASA projects from different centers, 1971–1987) was used as a completely held-out test set. The model was trained on COCOMO-81 only and evaluated on NASA-93 with no hyperparameter retuning — a strict out-of-sample test.

EvaluationDatasetnMMREPRED(25)
Leave-One-Out CV COCOMO-81 63 0.3132 47.6%
Out-of-sample test NASA-93 93 0.5480 43.0%

The cross-dataset MMRE of 0.548 is higher than the LOO-MMRE, which is expected — NASA-93 contains a different distribution of projects (69 semi-detached vs 24 in COCOMO-81). The fact that 43% of entirely unseen projects are predicted within 25% of actual demonstrates genuine generalization.

9. Limitations & Future Work

9.1 Current Limitations

Training data age: COCOMO-81 projects are from the 1980s. Modern software development — Agile sprints, microservices, cloud-native infrastructure, AI coding tools — is not represented. Results should be treated as directional estimates, not budget commitments.
LimitationDetails
SVR vs LSSVM The paper uses LSSVM (Least Squares SVM, equality constraints, dense solution). This implementation uses standard ε-SVR (sklearn). Both are kernel machines with RBF — the core methodology is preserved.
Automated FAHP matrix The paper constructs pairwise matrices manually with expert judgment. This implementation derives them automatically from Spearman correlations. The weights differ but the mechanism is the same.
Dataset size 63 projects is small. Wide PI ([−40%, +64%]) reflects this uncertainty.
GenAI multipliers Copilot/Cursor productivity adjustments are post-hoc multipliers from external studies, not trained into the model.

9.2 Proposed Mitacs Extension

The central Mitacs research proposal is to replace COCOMO-81 with a company's own historical project data. Modern teams generate far richer signals:

JiraStory points, sprint velocity, backlog churn, issue cycle timeLOC, CPLX

Architecture docsMicroservices count, API integrations, cloud servicesVIRT, TIME, STOR

The same FAHP + weighted-kernel SVR methodology would be applied to this modern dataset. SHAP would then reveal which company-specific signals drive cost overruns on their particular project types — a direct, actionable output for project managers.

Expected outcome: Significantly lower MMRE than 0.3132, because the model would be trained on data that actually reflects how the company works today, rather than 40-year-old defense software from a different technological era.
